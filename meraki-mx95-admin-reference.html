MX-hosted DHCP server configuration, reservations, and DNS proxy behavior.

MX acts as DHCP server for the VLAN. Configurable pool, lease time, DNS, options.

Inbound Rules (WAN → LAN)

MX denies all unsolicited inbound traffic by default. Only configure inbound rules for services explicitly exposed to the internet (e.g., published web servers, VoIP SBCs).

  • Navigate to: Security & SD-WAN → Firewall → Inbound Rules
  • 1:1 NAT or Port Forwarding required to map WAN IP:Port → LAN host
  • Pair inbound firewall allow rules with IDS signatures to monitor exposed services

Layer 7 Application Firewall

Application-aware blocking using Meraki's DPI engine, independent of port/IP.

The MX uses deep packet inspection to identify applications regardless of port. L7 rules are evaluated per-flow after L3 rules and can block or limit specific apps.

Navigation

Security & SD-WAN → Firewall → Layer 7 Firewall Rules

Block Categories (Examples)

Peer-to-Peer BitTorrent TOR Anonymizers Online Gaming Video Streaming Social Media Crypto Mining File Storage Adult Content Remote Access Tools Proxy/Anonymizer HTTPS Evasion Tools

Group Policies

L7 rules can be applied globally or via Group Policies assigned to specific clients, SSIDs, or VLANs. This allows different app-blocking rules for guest vs. corporate vs. IoT segments.

ℹ️
HTTPS Inspection Note: MX does not perform SSL/TLS interception. L7 identification of encrypted traffic relies on SNI, JA3 fingerprinting, and IP reputation. Some encrypted traffic may not be identifiable by application name.

AMP / Malware Protection & Threat Intelligence

Cisco Advanced Malware Protection — file inspection via cloud hash lookup.

AMP scans files passing through the MX (HTTP/HTTPS downloads, email attachments via SMTP proxy) by computing SHA-256 hashes and querying Cisco Talos threat intelligence cloud.

Configuration

Security & SD-WAN → Threat Protection → Advanced Malware Protection

AMP Mode
Enable AMP for all traffic, or HTTP only. Toggle under Threat Protection. Requires Advanced Security license.
Hash Lookup
Files are NOT uploaded to the cloud. Only the SHA-256 hash is submitted to Talos. Disposition: Clean / Malicious / Unknown.

Threat Intelligence (URL & IP Reputation)

  • MX checks URLs against Cisco Talos reputation feeds in real time
  • Blocks connections to known C2 servers, phishing pages, and malware distribution sites
  • Disposition visible in Event Log: Security Center → Events → AMP Events
  • Retrospective alerts: Talos may reclassify a file post-download; MX Dashboard alerts on disposition change

Filtering Layers

Block entire URL categories (Adult, Gambling, Malware, P2P, etc.) sourced from Webroot BrightCloud.

Explicit per-URL overrides. Allowlist takes precedence over category blocks. Supports wildcards (*.example.com).

Safe Search & YouTube Restriction

  • Force Safe Search on Google, Bing, YouTube, DuckDuckGo
  • YouTube Restricted Mode enforcement via DNS redirect to restricted.youtube.com
  • Applies to all HTTP/HTTPS traffic passing through MX (effective for non-split-tunnel VPN clients too)

Blocked Page Customization

Configure a custom block message with organization branding at Organization → Configure → Blocked Page.

ℹ️
HTTPS Filtering: For HTTPS sites, the MX can block based on SNI (server name in TLS handshake) without full SSL inspection. Categories relying on page content analysis are only effective on HTTP. Consider pairing with a cloud web proxy (Cisco Umbrella) for full HTTPS visibility.

AutoVPN (Meraki Site-to-Site)

Zero-config encrypted VPN fabric across all Meraki MX appliances in the org.

How AutoVPN Works

  • MX appliances register WAN IP/UDP port info with Meraki cloud registry
  • Peers discover each other and establish encrypted UDP tunnels automatically
  • No pre-shared keys, ISAKMP config, or peer IP configuration required
  • Uses AES-128 (default) or AES-256 encryption with ECDH key exchange
  • Dashboard shows real-time VPN topology under Organization → VPN Status

Hub vs. Spoke Mode

Hub Mode
MX acts as VPN concentrator. Spoke sites route through hub. Supports default route override (full-tunnel) for centralized internet egress through HQ.
Spoke Mode
MX connects to one or more hub MX appliances. Spoke-to-spoke traffic transits hub unless direct spoke-to-spoke is enabled.

VPN Subnet Advertisement

# Per-VLAN toggle — Dashboard: Addressing & VLANs
VLAN 10  Corporate   Use VPN: YES  ← advertised to peers
VLAN 20  Servers     Use VPN: YES
VLAN 30  Guest       Use VPN: NO   ← NOT advertised
VLAN 40  IoT         Use VPN: NO   ← NOT advertised

Full-Tunnel (Default Route Override)

⚠️
Full Tunnel: Configure on spoke sites to route all internet traffic through the hub MX. Hub must have appropriate outbound NAT and internet breakout. Adds latency for internet-bound traffic at remote sites. Consider split-tunnel for Office 365/SaaS.

Warm Spare (High Availability)

Active/passive HA pair using a dedicated spare MX95 unit.

How Warm Spare Works

  • Primary MX handles all traffic; spare is in standby, monitoring primary via HA heartbeat
  • If primary fails, spare promotes itself and takes over WAN/LAN interfaces within ~1 min
  • Both units share the same configuration — managed as a single Dashboard device
  • Both units share the same WAN IP (primary holds it; spare assumes it on failover)
  • LAN uses virtual IP (VIP) shared by both; clients use VIP as default gateway

HA Setup Requirements

  1. Claim both MX units in Dashboard under the same network.
  2. Navigate to Security & SD-WAN → Warm Spare. Select the spare unit.
  3. Connect both units to the same WAN and LAN switch segments.
  4. Configure a dedicated HA link (Ethernet cable, port 1 on both units) for heartbeat.
  5. Set LAN Virtual IP (VIP) — clients and routing point to this IP.
  6. Test failover by simulating a primary failure; verify traffic resumes via spare.

HA Parameters

Primary MX:        MX95-A
Spare MX:          MX95-B
HA Port:           Port 1  (dedicated HA link)
LAN Virtual IP:    10.10.10.1  (used by all VLAN gateways)
WAN VIP:           shared — primary holds, spare assumes on failover
Failover Time:     ~60 seconds
🚫
Do not run both MX units on the same uplink without understanding STP. Ensure downstream switches are configured to handle the MAC address takeover during failover. Avoid bridging loops — verify spanning tree configuration before deploying HA.

Security Hardening Checklist

Administrative hardening checklist for production MX95 deployments.

Dashboard & Access

  1. Enable MFA on all Dashboard administrator accounts (Organization → Administrators).
  2. Apply least-privilege Dashboard roles — avoid giving all admins full org-level access.
  3. Review and remove unused admin accounts quarterly.
  4. Set IP-based dashboard access restriction (Organization → Login security → IP allowlist).
  5. Enable change logging / audit trail (Organization → Change log).

Firewall & Traffic

  1. Change the default outbound firewall rule to Deny All.
  2. Remove any inbound rules permitting broad internet access to internal hosts.
  3. Confirm Guest and IoT VLANs have inter-VLAN deny rules to corporate segments.
  4. Review port-forwarding rules — document and justify each exposed service.
  5. Disable any unused WAN ports.

Security Services

  1. Enable IDS in Detection mode first; review events for 1–2 weeks.
  2. Tune false positives, then switch IDS → IPS Prevention mode.
  3. Enable AMP malware protection on all HTTP/HTTPS flows.
  4. Enable Content Filtering and block at minimum: Malware, Spyware, Phishing.
  5. Block high-risk L7 app categories: TOR, proxy/anonymizers, P2P, crypto mining.

VPN

  1. Remove any VPN subnets that don't need to be advertised to remote sites.
  2. Verify 3rd-party IPsec peers use AES-256 + SHA-256 + DH14+ (no 3DES, MD5, Group 2).
  3. Restrict Client VPN to a dedicated subnet; apply a restrictive group policy to VPN clients.
  4. Require RADIUS + MFA for Client VPN authentication (e.g., RADIUS + Duo).

HA & Resilience

  1. Deploy Warm Spare if the environment requires <5 min RTO for firewall failure.
  2. Configure both WAN uplinks with independent ISPs (different physical paths if possible).
  3. Schedule firmware upgrades during low-traffic maintenance windows.
  4. Test HA failover in a maintenance window annually.

Monitoring

  1. Configure email + webhook alerts for: appliance offline, uplink down, IPS events, HA failover.
  2. Forward syslog to a SIEM (at minimum: security events + VPN).
  3. Review the Security Center weekly for IPS/AMP event trends.
  4. Review Top Applications report monthly; investigate unexpected high-usage applications.
